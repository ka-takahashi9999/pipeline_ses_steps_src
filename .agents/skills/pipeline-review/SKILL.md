レビュー専用。**コード修正・ファイル更新は禁止**。指摘と修正方針のみ出す。

## モード

| 呼び出し | モード | 範囲 |
|---|---|---|
| 引数なし | 通常レビュー | 達成条件・出力整合・実装妥当性 |
| `strict` | 厳しめレビュー | 通常 + 設計逸脱 / 副作用 / 将来事故 |

## 出力順序（最優先）
1. **findings を先に出す**
2. 問題あり → 重大度順（高 / 中 / 低）
3. 問題なし → 「重大な問題なし」を先に明言してから補足（軽微な懸念は最大2点）
4. 長い前置き・背景説明を書かない

findings の書式:
```
[高/中/低] 問題箇所
根拠: 実ファイル名・行番号・実行結果
修正方針: （実装はしない）
```
推測ではなく、実ファイル・実行結果ベースで書く。

## 確認順序
1. 完了条件
2. 代表ケース（3件）
3. 件数整合・分布
4. 全体傾向
5. 問題なければ深掘りしない

## 通常レビューで見る点
- JSONLが1行1JSONになっているか
- 必須キー欠落がないか
- 型崩れ（数値 / 文字列 / 空文字混入）がないか
- default値と `*_source` の整合
- エラー時の記録漏れ・例外握りつぶし
- 例外系・空データ系の考慮漏れ
- 依頼対象外への不要な修正混入

## strict で追加確認する点
- step責務逸脱
- JSONL / schema 互換性の崩れ、根拠のないスキーマ変更
- `message_id` の接続破綻、後続stepからの逆参照
- default / `*_source` の不整合、解析不能データの黙殺
- 不要な副作用（他stepへの影響、出力先・ファイル名の不整合）
- 冪等性（同一入力で再実行して結果が変わらないか）
- 再実行耐性（途中失敗後の再実行、部分出力の残留）
- 将来事故（表面上は動くが運用・保守で破綻する実装）
- 責務不足を別stepの場当たり補正で吸収していないか

## 出力制約
- JSONL全文・ログ全文・コード全文を貼らない
- 代表3件のみ示す。全件列挙しない
- 1回の返答で大量のline引用をしない
- 問題なしなのに冗長な説明を続けない
- 無関係なstepまで掘らない
- `explain_.md` / `PIPELINE_OVERVIEW.md` は明示指示がない限り参照しない
